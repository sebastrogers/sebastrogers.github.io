FASE 1-1 · CONTEÚDO NOVO

Esperar sem travar

Por que o navegador não pode ficar parado esperando a resposta da rede.

CONCEITOAula 13

Síncrono e assíncrono

O código que vocês escreveram até aqui é síncrono: uma linha só começa quando a anterior termina. Isso funciona para contas, que levam microssegundos. Um pedido pela rede leva centenas de milissegundos, às vezes segundos. Código assíncrono é o que dispara a tarefa demorada, segue em frente e trata o resultado quando ele chegar.

exemplo
síncrono                   assíncrono
--------                   ----------
pede o café                pede o café e pega a senha
fica no balcão esperando   senta e conversa
recebe e só então senta    chamam a senha: busca o café

a fila trava               o salão continua andando
Pense assimO garçom que fica parado na cozinha até o prato sair atende uma mesa por vez. O bom garçom anota, entrega na cozinha e volta ao salão; quando o prato fica pronto, ele leva.
CONCEITOAula 13

Uma linha de execução só

O JavaScript da página roda numa linha de execução só (em inglês, single thread): a mesma que desenha a tela e responde ao clique. Se o código ficasse parado esperando a rede, a página inteira congelaria: nada de rolar, digitar ou clicar. Por isso tudo o que demora no navegador é assíncrono: o pedido fica com o navegador, e o seu código é avisado depois.

exemplo
console.log("1. pedi os produtos");

setTimeout(() => {
  console.log("3. chegaram");      // roda depois
}, 1000);

console.log("2. sigo funcionando");

// no console: 1, 2 e, um segundo depois, 3
CuidadoA ordem em que as linhas estão escritas não é a ordem em que elas rodam. É a primeira coisa que confunde quem vem do Python síncrono, e a causa de metade dos bugs desta aula.
Fase 1-1 · Em que ordem aparece?

O que o console mostra, e em que ordem?

  • console.log("A");
  • setTimeout(() => console.log("B"), 0);
  • console.log("C");
  • Repare no zero: o setTimeout pede para esperar 0 milissegundos.

A, C, B.

Mesmo com zero, a função do setTimeout vai para a fila e só roda quando o código atual termina.

Assíncrono não quer dizer "demorado": quer dizer "depois, quando a linha de execução estiver livre".

FASE 1-2 · CONTEÚDO NOVO

Promessas

O objeto que representa um resultado que ainda não chegou.

CONCEITOAula 13

Promise: a senha do pedido

Uma Promise (promessa) é um objeto que representa um valor que vai chegar depois. Ela tem três estados: pendente (pending, ainda esperando), cumprida (fulfilled, chegou o valor) e rejeitada (rejected, deu erro). Toda função do navegador que conversa com a rede devolve uma promessa na hora, e o valor de verdade depois.

console do navegador
> const p = fetch("http://127.0.0.1:8000/produtos")
> p
Promise {<pending>}        // a senha, não o café

// um instante depois:
> p
Promise {<fulfilled>: Response}

// com a API desligada:
Promise {<rejected>: TypeError: Failed to fetch}
Pense assimA promessa é a senha do restaurante: você pega na hora, mas não dá para comer a senha. O que interessa é o que ela vira quando chamam o seu número.
CONCEITOAula 13

then e catch: o jeito antigo de esperar

Antes do await, esperava-se uma promessa encadeando funções: then (então) recebe o valor quando ela é cumprida, catch (pegar) recebe o erro quando ela é rejeitada. Vocês vão encontrar esse estilo em tutoriais e em código antigo, então vale reconhecer, mesmo que hoje a gente escreva de outro jeito.

exemplo
fetch("http://127.0.0.1:8000/produtos")
  .then(resposta => resposta.json())
  .then(produtos => console.log(produtos))
  .catch(erro => console.log("falhou:", erro));

console.log("isto aparece primeiro");
CuidadoCada then recebe o resultado do anterior. Com três ou quatro passos a corrente vira uma escada difícil de ler, e foi isso que levou a linguagem a criar o async e o await.
Fase 1-2 · Qual o estado da promessa?

Em que estado fica a promessa do fetch em cada caso?

  • a) Logo depois de chamar o fetch, na linha seguinte.
  • b) A API respondeu com a lista de produtos.
  • c) A API está desligada e o navegador não conseguiu conectar.
  • d) A API respondeu 404, produto não encontrado.

a) pendente. A rede ainda não respondeu.

b) cumprida, com a resposta dentro.

c) rejeitada, com TypeError: Failed to fetch.

d) cumprida! Para o fetch, a rede funcionou: houve resposta. O 404 é um assunto seu, e a fase 2-1 mostra como tratar.

FASE 1-3 · CONTEÚDO NOVO

async e await

Escrever código que espera como se fosse síncrono, sem travar a página.

CONCEITOAula 13

async e await

await (aguardar) pausa só a função até a promessa se resolver e entrega o valor de dentro dela. A página continua livre enquanto isso. A condição: await só vale dentro de uma função marcada com async. O resultado é um código que se lê de cima para baixo, como o Python de vocês.

front/app.js
async function carregar() {
  const resposta = await fetch(`${API}/produtos`);
  const produtos = await resposta.json();
  console.log(produtos);           // a lista de verdade
}

carregar();
console.log("a página segue viva");
Pense assimO await é o garçom esperando o prato daquela mesa. As outras mesas, isto é, os cliques, a digitação e a rolagem, continuam sendo atendidas.
CONCEITOAula 13

O await esquecido

Sem o await, a variável recebe a promessa, e não o valor. Nada quebra na hora: o erro só aparece duas linhas depois, quando o código tenta usar uma lista que na verdade é uma senha. E toda função async também devolve uma promessa, então quem chama precisa de await se quiser o resultado.

exemplo
const resposta = fetch(`${API}/produtos`);   // faltou await
console.log(resposta);
// Promise {<pending>}

const produtos = resposta.json();
// TypeError: resposta.json is not a function

// certo:
const resposta = await fetch(`${API}/produtos`);
CuidadoViu Promise {<pending>} no console, ou is not a function logo depois de um fetch? Procure o await que faltou.
CONCEITOAula 13

Erros com try e catch

Dentro de uma função async, uma promessa rejeitada vira um erro comum, que se trata com try e catch, como o try e except do Python. É assim que a página mostra uma mensagem amigável em vez de ficar em branco quando a API está fora do ar.

exemplo
# Python                         // JavaScript
try:                             try {
    r = requests.get(url)          const r = await fetch(url);
except Exception as erro:        } catch (erro) {
    print("falhou", erro)          console.log("falhou", erro);
                                 }
CuidadoO catch só pega o que foi aguardado dentro do try. Um fetch sem await escapa do try e o erro aparece solto, em vermelho, no console.
Fase 1-3 · O que aparece no console?

Leia o código e diga o que cada console.log imprime.

  • async function total() { return 42; }
  • a) console.log(total());
  • b) console.log(await total());, dentro de outra função async
  • c) const r = fetch(url); console.log(r.ok);

a) Promise {<fulfilled>: 42}. Função async sempre devolve uma promessa, mesmo com return 42.

b) 42. O await abre a promessa e entrega o valor.

c) undefined. Sem await, r é a promessa, e promessa não tem ok. É o bug silencioso da fase.

FASE 2-1 · CONTEÚDO NOVO

Buscar com fetch

O pedido GET saindo do navegador e a resposta chegando como objeto.

CONCEITOAula 13

fetch: o GET do navegador

fetch (buscar) faz um pedido HTTP e devolve uma promessa de Response (resposta). São dois await: o primeiro espera os cabeçalhos chegarem; o segundo, resposta.json(), espera o corpo e converte o JSON em array e objetos de JavaScript. É o mesmo JSON que vocês viam no /docs da API.

front/app.js
const API = "http://127.0.0.1:8000";

async function carregar() {
  const resposta = await fetch(`${API}/produtos`);
  console.log(resposta.status);      // 200
  const produtos = await resposta.json();
  console.log(produtos[0].nome);     // "Camiseta básica"
}

// com filtro, a query string da Aula 9:
await fetch(`${API}/produtos?tamanho=M`);
Pense assimÉ o mesmo pedido que o TestClient fazia nos testes da Aula 9: cliente.get("/produtos"). Só que agora quem pede é a página, no navegador da pessoa.

CONCEITOAula 13

404 não é erro para o fetch

O fetch só rejeita a promessa quando não houve resposta: API desligada, endereço errado, sem rede. Se a API respondeu, mesmo com 404 ou 500, a promessa é cumprida. Quem decide se deu certo é você, olhando resposta.ok, que vale true para os status de 200 a 299.

front/app.js
const resposta = await fetch(`${API}/produtos/99`);

resposta.status    // 404
resposta.ok        // false

if (!resposta.ok) {
  throw new Error(`a API respondeu ${resposta.status}`);
}
const produto = await resposta.json();
CuidadoSem checar resposta.ok, o código segue feliz e tenta desenhar {"detail": "produto 99 não encontrado"} como se fosse um produto.
FASE 2-2 · CONTEÚDO NOVO

Enviar com POST

Mandar o que a pessoa digitou para a API gravar no banco.

CONCEITOAula 13

POST com JSON

Para enviar, o fetch recebe um segundo argumento com três coisas: o method (método), os headers (cabeçalhos) e o body (corpo). O cabeçalho Content-Type avisa que vai JSON, e JSON.stringify converte o objeto em texto. Os campos são os mesmos do ProdutoEntrada da API.

front/cadastro.js
const dados = { tipo: "Produto", nome: "Boné",
                preco: 49.9, tamanho: "G" };

const resposta = await fetch(`${API}/produtos`, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify(dados),
});

resposta.status            // 201, Created
const novo = await resposta.json();
novo.id                    // o número que o banco deu
Pense assimJSON.stringify é o json.dumps do Python; resposta.json() é o json.loads. Na rede só passa texto.
CONCEITOAula 13

Ler o erro que a API devolve

Quando a API recusa, ela explica no corpo da resposta, no campo detail: foi assim que vocês escreveram os exception_handler da Aula 10. O front-end só precisa ler esse campo e mostrar na tela. A regra continua no servidor; a tela apenas avisa.

front/cadastro.js
const corpo = await resposta.json();

if (!resposta.ok) {
  aviso.textContent = `Não cadastrou: ${corpo.detail}`;
  return;
}
aviso.textContent = `${corpo.nome} cadastrado com o número ${corpo.id}.`;

// 409: Não cadastrou: já existe um produto chamado Boné
// 422: quando os dados não batem com o ProdutoEntrada
CuidadoValidar no front-end, como na Aula 12, é conforto para quem usa; validar no servidor é segurança. Qualquer pessoa pode chamar a API sem passar pela sua tela.
Fase 2-2 · Por que deu 422?

Os quatro POSTs abaixo falham. O que está errado em cada um?

  • a) body: dados, sem JSON.stringify
  • b) sem a linha do headers
  • c) preco: document.querySelector("#preco").value
  • d) { nome: "Boné", valor: 49.9, tamanho: "G" }

a) O navegador manda [object Object] como texto. A API não consegue ler o JSON: 422.

b) Sem Content-Type: application/json, o FastAPI não trata o corpo como JSON: 422.

c) Funciona por sorte: .value é texto e o Pydantic converte "49.9". Mas mande Number(...): o contrato é número.

d) O campo se chama preco no ProdutoEntrada, não valor. Falta o obrigatório: 422.

FASE 2-3 · CONTEÚDO NOVO

CORS

Por que o navegador bloqueia a própria API de vocês, e quem libera.

CONCEITOAula 13

Origem: protocolo, endereço e porta

Para o navegador, uma origem é a soma de protocolo, endereço e porta. Por segurança, uma página só lê respostas da mesma origem em que foi aberta. Na aula, as páginas rodam na porta 5500 e a API na 8000: para o navegador, são dois sites diferentes.

exemplo
página:  http://127.0.0.1:5500/index.html
API:     http://127.0.0.1:8000/produtos
                         ^^^^ porta diferente = outra origem

// no console, em vermelho:
Access to fetch at 'http://127.0.0.1:8000/produtos'
from origin 'http://127.0.0.1:5500' has been blocked
by CORS policy: No 'Access-Control-Allow-Origin'
header is present on the requested resource.
Pense assimA regra protege o usuário: sem ela, qualquer site aberto numa aba poderia ler dados de outro site em que a pessoa está logada.
CONCEITOAula 13

CORS: quem libera é o servidor

CORS é Cross-Origin Resource Sharing, compartilhamento de recursos entre origens. É a forma de a API dizer ao navegador quais origens podem ler as respostas dela. A liberação vai no servidor, com um cabeçalho na resposta; mudar o fetch não resolve. No FastAPI, são algumas linhas no api.py.

api.py
from fastapi.middleware.cors import CORSMiddleware

app = FastAPI(title="Loja de Roupas", lifespan=ciclo_de_vida)

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://127.0.0.1:5500",
                   "http://localhost:5500"],
    allow_methods=["*"],
    allow_headers=["*"],
)
Cuidadoallow_origins=["*"] faz o erro sumir, e libera a API para qualquer site da internet. Liste as origens de vocês. E 127.0.0.1 e localhost são origens diferentes: liste as duas.
Fase 2-3 · Bloqueia ou não?

Com a API liberando só http://127.0.0.1:5500, a vitrine consegue ler os produtos?

  • a) Página aberta em http://127.0.0.1:5500
  • b) Página aberta em http://localhost:5500
  • c) Página aberta com dois cliques no arquivo, file:///.../index.html
  • d) O mesmo pedido feito no /docs ou pelo pytest

a) lê. Origem listada.

b) bloqueia. localhost e 127.0.0.1 são origens diferentes para o navegador.

c) bloqueia. Arquivo aberto do disco não tem origem de rede. Rode as páginas com python -m http.server 5500.

d) funciona. CORS é regra do navegador: o /docs é da mesma origem da API, e o pytest nem é navegador.

  const resposta = await fetch(`${API}/produtos`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(dados),
  });
  const corpo = await resposta.json();
  if (!resposta.ok) {
    aviso.textContent = `Não cadastrou: ${corpo.detail}`;
    return;
  }
  aviso.textContent = `${corpo.nome} cadastrado com o número ${corpo.id}.`;
  form.reset();
});
  • A função do submit ganhou async: sem ele, o await lá dentro é erro de sintaxe.
  • No cadastro.html: id="form-produto" no form, um <p id="aviso" role="status"> depois dele e o <script src="cadastro.js"> no fim do body.
  • Os quatro campos são os do ProdutoEntrada, e o teste da Aula 11 já vigiava isso.

// no index.html, logo abaixo do h2:
//   <p id="estado" role="status"></p>
const estado = document.querySelector("#estado");

async function carregar() {
  estado.textContent = "Carregando produtos...";
  try {
    const resposta = await fetch(`${API}/produtos`);
    if (!resposta.ok) {
      throw new Error(`a API respondeu ${resposta.status}`);
    }
    produtos = await resposta.json();
    desenhar(produtos);
    estado.textContent = produtos.length === 0
      ? "Nenhum produto cadastrado ainda." : "";
  } catch (erro) {
    estado.textContent = "Não foi possível falar com a API. Ela está ligada?";
    console.error(erro);
  }
}
  • Uma tela de dados tem quatro estados: carregando, com dados, vazia e com erro. A tela em branco não comunica nenhum.
  • O throw manda o 404 e o 500 para o mesmo catch da API desligada: uma mensagem só para "não deu".
  • console.error guarda o detalhe técnico para vocês; a pessoa lê a frase em português.
  • No cadastro.js, o mesmo try e catch em volta do fetch, com a mesma mensagem no aviso.
