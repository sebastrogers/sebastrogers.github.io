RELEMBREAula 2

Três tipos de requisito

Funcional: o que o sistema faz. Não funcional: com que qualidade ele faz. Regra de negócio: uma política do cliente, que vale com ou sem sistema.

Pense assimNa loja: o provador existe (funcional), é limpo e iluminado (não funcional), e só se leva até 3 peças por vez (regra).
Cuidado"O sistema deve usar Python" não é necessidade do cliente: é uma escolha técnica, e precisa de origem para estar no DDR.
exemplo
RF-03   O sistema deve calcular o frete do carrinho.
RNF-01  A vitrine deve carregar em até 2 s com 100 usuários.
RN-01   Compras a partir de R$ 200 têm frete grátis.
RELEMBREAula 2 · ISO/IEC/IEEE 29148

As características de um bom requisito

O checklist da revisão de hoje. Cada característica vira uma pergunta que o revisor faz ao texto.

exemplo
Não ambíguo   duas pessoas leem do mesmo jeito?
Verificável   dá para testar com sim ou não?
Singular      pede uma coisa só?
Completo      falta ator, exceção ou critério?
Necessário    tem origem? alguém pediu?
Consistente   contradiz outro requisito?
Rastreável    tem ID, origem e história?
Conforme      segue o modelo e a escrita?
Fase 1-1 · Conserte

O que há de errado em cada um?

requisitos da Loja de Roupas
RNF-02  O site deve ser rápido.

RF-07   O sistema deve calcular o frete e enviar o e-mail
        de confirmação do pedido.

RN-01   Frete grátis acima de R$ 200.
H04     Dado uma compra de exatamente R$ 200,
        quando finalizo, então o frete é grátis.

RNF-02: não é verificável. "Rápido" não tem número. Sugestão: até 2 s com 100 usuários.

RF-07: não é singular. São dois pedidos: frete e e-mail.

RN-01 e H04: não são consistentes. "Acima de 200" exclui o 200; o critério inclui. Exatamente na fronteira, onde um teste automatizado pegaria a contradição.

RELEMBREAula 7

Defeito e gravidade

Um defeito bem registrado diz onde está, qual regra quebra, por quê e como poderia ficar. A gravidade diz a urgência.

CuidadoUma ficha com dez erros de digitação vale menos que uma com dois defeitos críticos bem explicados.
exemplo
CRÍTICO  leva a construir a coisa errada ou contradiz outra parte
MAIOR    impede testar ou entender sem perguntar ao autor
MENOR    forma, digitação, padrão

RELEMBREAula 5

Critério de aceite

Diz como saber que uma história está pronta, no formato Dado (o contexto), Quando (a ação), Então (o resultado que dá para conferir).

exemplo
H04  Como cliente, quero frete grátis em compras grandes,
     para economizar.

Critério: Dado um carrinho de R$ 200,00,
          quando finalizo a compra,
          então o frete é R$ 0,00.

DESENVOLVIMENTO · teste em Python

Teste automatizado

teste

Critério verificável vira teste quase palavra por palavra. Se não dá para escrever o teste, provavelmente o requisito tem um defeito.

Fase 3-1 · Para começar

"Como cliente, quero finalizar a compra, para receber as roupas em casa." Está claro o que o sistema faz?

O que o cliente informa primeiro? Quando o frete é calculado? E se o pagamento for recusado? A história não responde. É para isso que serve o caso de uso.

RELEMBREConteúdo novo · Jacobson, 1992

Caso de uso

Descrição, passo a passo, de como um ator usa o sistema para alcançar um objetivo, incluindo o que pode dar errado no caminho.

Pense assimO roteiro de um atendimento no caixa: o que o cliente diz, o que o caixa responde, e o que fazer quando o cartão é recusado.
exemplo
Nome           UC03 Finalizar compra
Ator principal Cliente
Objetivo       comprar as peças do carrinho
Fluxo          os passos, alternando ator e sistema
Exceções       o que pode dar errado
RELEMBREConteúdo novo

Ator

Quem está fora do sistema e interage com ele. É um papel, não uma pessoa. Pode ser gente ou outro sistema.

CuidadoO banco de dados não é ator: ele está dentro do sistema.
exemplo
Ator principal    Cliente         inicia o caso de uso
Ator secundário   Pagamento       outro sistema que ajuda
Outro ator        Dona da loja    papel diferente, casos diferentes

A mesma pessoa pode ser cliente e dona: são dois papéis.

Fase 3-1 · Exemplo guiado

UC03: o fluxo principal

fluxo principal
1. Cliente abre o carrinho e escolhe "Finalizar compra".
2. Sistema mostra as peças, o subtotal, o frete e o total.
3. Cliente informa o endereço de entrega.
4. Sistema recalcula o frete pelo endereço (RN-01).
5. Cliente escolhe a forma de pagamento.
6. Sistema envia a cobrança ao sistema de pagamento.
7. Sistema de pagamento confirma a cobrança.
8. Sistema registra o pedido, baixa o estoque e
   mostra o número do pedido.
  • Cada passo é uma ação, de um lado só: ator ou sistema.
  • É o "caminho feliz": tudo dá certo.
  • Sem tela, sem botão, sem tecnologia: "escolhe", e não "clica no botão azul".
Fase 3-1 · Qual passo está errado?

Revise este fluxo

fluxo de um colega
1. Cliente clica no botão verde "Comprar".
2. Sistema faz SELECT na tabela de produtos.
3. Cliente informa o endereço.
4. Sistema calcula o frete e o cliente paga.

1: descreve a tela (botão verde). Escreva a intenção: "Cliente escolhe comprar".

2: descreve tecnologia interna (SELECT). Escreva o que o ator percebe: "Sistema mostra as peças".

4: dois atores no mesmo passo. Separe em "Sistema calcula o frete" e "Cliente paga".

RELEMBREConteúdo novo

Fluxo alternativo e de exceção

O alternativo é outro caminho que também chega ao objetivo. O de exceção é quando algo dá errado e o objetivo não é alcançado, ou é adiado.

CuidadoToda exceção diz em qual passo começa e como termina: volta a um passo ou encerra o caso de uso.
exemplo
Alternativo  A1 (passo 5) Cliente aplica um cupom:
             sistema valida, recalcula o total e volta ao passo 5.

Exceção      E1 (passo 7) Pagamento recusado:
             sistema mostra o motivo e volta ao passo 5;
             o pedido não é registrado.
Fase 3-2 · Exemplo guiado

UC03: alternativos e exceções

fluxos
A1 (passo 3) Cliente usa um endereço já salvo:
   sistema preenche o endereço e segue para o passo 4.
A2 (passo 5) Cliente aplica um cupom:
   sistema valida, recalcula o total e volta ao passo 5.

E1 (passo 7) Pagamento recusado:
   sistema mostra o motivo e volta ao passo 5.
E2 (passo 8) Peça sem estoque:
   sistema avisa, retira a peça e volta ao passo 2.
E3 (passo 4) Endereço fora da área de entrega:
   sistema avisa e encerra o caso de uso.
  • Os números dizem onde cada desvio começa.
  • Cada exceção é um caso de teste pronto: "Dado pagamento recusado, quando..., então...".
  • E3 mostra uma exceção que encerra, em vez de voltar.
RELEMBREConteúdo novo · UML

include e extend

Ligações entre casos de uso. include: um caso sempre usa outro. extend: um caso às vezes acrescenta comportamento a outro.

CuidadoA seta do extend aponta para o caso que é estendido. Na dúvida, prefira um fluxo alternativo a um extend.
exemplo
Finalizar compra --«include»--> Calcular frete
   (toda compra calcula frete)

Aplicar cupom --«extend»--> Finalizar compra
   (só quando o cliente tem cupom)

Fase 3-2 · Include ou extend?

Como ligar estes casos de uso?

situações
a) Finalizar compra e Emitir nota fiscal
   (toda compra finalizada emite nota)

b) Finalizar compra e Embrulhar para presente
   (só quando o cliente pede)

a) include: acontece sempre. Finalizar compra «include» Emitir nota fiscal.

b) extend: acontece às vezes. Embrulhar para presente «extend» Finalizar compra.
